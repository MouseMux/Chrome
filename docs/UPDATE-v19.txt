MouseMux Chrome Patches v19 - Build #58 - 2026-09-02
=====================================================

Chromium base: 151.0.7922.77 (unchanged from 2.2.57)
Client version reported to the SDK: 2.2.58

A field report on 2.2.57 from a customer running two users found two things
wrong, both of them real. Fixing them turned into a rebuild of the control
dialog, because the diagnosis needed information the dialog had never shown.


1. KEYBOARDS REACHING THE WRONG WINDOW

   Reported as: with both users captured, both keyboards typed into the first
   user's window.

   Two independent causes, either of which produces exactly that.

   THE PAIRING MAY NOT EXIST. Every keystroke arrives carrying a KEYBOARD
   hwid, and all per-user state is keyed by MOUSE hwid, so OnKeyboardKey
   translates one to the other through keyboard_to_mouse_hwid_ - built from
   the SDK user list, from users that hold both a pointer and a keyboard. A
   user with a pointer alone produces no entry, and the lookup fails.

   The old fallback handed those keystrokes to owner_hwid_, the primary owner.
   That was correct while one device could drive Chrome: one owner, one
   possible destination, no guess involved. It silently became a guess when
   owners went plural, and the guess is always the same person - so with an
   unassigned keyboard, everybody types into the first user's window.

   With several owners we no longer guess. An unattributable keystroke is
   dropped, and so is one from a keyboard whose user owns no window - keyboard
   events were never gated on ownership, because with one owner the server's
   own hook meant only one keyboard could reach us. Both drops are recorded
   for the dialog. Losing a keystroke is recoverable; typing into a
   colleague's document is not.

   Single-owner behaviour is untouched: one window, one destination, nothing
   to get wrong.

   An unpaired keystroke also re-requests the user list, at most once every
   five seconds, so a pairing made in MouseMux while the browser is running is
   picked up rather than waiting for a restart.

   THE CLAIM MAY NOT HAVE REACHED THE KEYBOARD. A click only set
   keyboard_target_view if it landed on page content. A click on a tab, the
   address bar or a bookmark goes down the aura path and returned before the
   line that follows a click with the keyboard - so a user whose first click
   was on Chrome's own interface owned a window as far as the mouse was
   concerned and had no keyboard target at all. Their typing fell through to
   "first showing view", which is the earliest window, which is the first user
   again.

   DispatchToAuraHost is now split: FindAuraTargetWindow() decides which
   toplevel window the click is in, DispatchToAuraHost() posts to it. A
   mousedown there claims that window for the device's keyboard, so clicking a
   tab picks a window up exactly as clicking the page does. The hard lock
   applies on that path too - a click on another user's tab strip is still a
   click in their window, and this path was the way around the lock.


2. "+ WINDOW" NOW HANDS OUT A SIGNED-IN WINDOW

   Reported as: sign in, press + Window, and the new window is signed out.
   Signing in there ends the first session, on a site that permits one.

   + Window called NewEmptyWindow. Cookies come from the profile so most sites
   carry over, but session storage belongs to the TAB, and a new window starts
   with an empty one. A web application holding its token there sees a new
   window as a new sign-in.

   It now duplicates the active tab and moves the copy to a new window, which
   is the customer's own workaround in one click. WebContents::Clone ->
   NavigationControllerImpl::CopyStateFrom clones the session storage
   namespace, and moving the tab carries the live WebContents across without a
   reload.

   CONSEQUENCE: sign in BEFORE handing windows out. A copy can only carry a
   session that already exists, and every handed-out window opens on whatever
   page the first window is showing.


3. THE DIALOG

   Neither fault above was visible from outside the browser, and the owner
   list made it worse by looking healthy: it showed where each user was
   WORKING, which is the same thing as where their typing lands only when the
   routing is right.

   Each row now carries a status dot (green captured, amber claimed but not
   captured, red no keyboard), the keyboard MouseMux has attached to that
   user, and which SCREEN they are on - by the number Windows uses, read from
   the monitor's device name, because indexing into the display list gives an
   arbitrary order that reported "Screen 2" for a window on screen 1. A line
   under the list shows where recent keystrokes actually landed. Routing
   decisions only, no key codes, so it stays on in release builds.

   Three panes - connection, users, options - because the dialog covers three
   unrelated subjects and ran them together in one column of identical
   toggles. Connection is a status line, a green indicator and one button.
   Capture became a per-row checkbox, which is a state rather than an action
   and frees "Release" to mean what it should: hand the window back. The old
   "Drop" is that Release; the big capture-everything button is gone.

   + Window and + Seat moved into the users heading. They used to share a row
   with the hotkey dropdown, which took the width and left both buttons
   elided; a minimum size cannot save a row whose total minimum exceeds the
   dialog.

   Everything greys out while disconnected, since none of it can do anything.
   Closing the dialog now closes the seat - the windows it hands out have no
   controls of their own, so leaving it closed with users captured strands
   everybody - and the button says Quit rather than Close.

   A Help window: white, scrollable, its own frame, covering every control and
   the order to do things in. It is exempt from native input blocking like the
   control dialog, or it would open and refuse every click including its own.

   Reports the MouseMux version it is connected to. The server has always sent
   server.info.notify.M2A on connect, carrying its version and protocol
   version; we were discarding it.


4. THE LIST, AT SCALE

   The user list scrolls, and rows are updated in place rather than rebuilt.

   Both come from the same bug. The list was a plain view given whatever
   vertical space was left over, and when that was not enough BoxLayout did
   not overflow - it squeezed the last child. With two users the second row
   was SIX pixels tall: its labels were clipped away by the row's own bounds,
   while its checkbox and buttons, which are layer-backed for their ink drops,
   carried on being composited. Half a row appeared, and the half that
   vanished was the half naming the user.

   That took four attempts to find, three of them aimed at painting, because
   from the outside it looked like a repaint problem - moving the window fixed
   it. The dialog now reports its own view tree through the control server
   (bounds, visibility, text, per cell), which turned it into one query.

   A scroll view cannot squeeze anybody, so rows always get their height and
   the list scrolls past about seven. And since the refresh runs every second,
   rebuilding the rows only when the SET of users changes matters at
   sixteen or twenty-four people: a title changing as somebody browses used to
   rewrite every view in the list. It now writes into the labels already
   there, which also means the tooltip under the operator's pointer survives.

   Controller callbacks post the rebuild rather than running it inline. A
   rebuild on the injected-input stack drew only part of what it built; the
   same rebuild as its own task drew correctly every time.


5. COMPILE SWITCHES

   Unchanged from 2.2.57.

   Shipped and on:  AURA_UI_CLICK_THROUGH, NATIVE_BLOCK, PEN_TOUCH_INJECT,
                    MULTI_OWNER, KEYBOARD_LAYOUT
   Experiments off: PEN_TOUCH_BLOCK, NATIVE_BLOCK_HARD, NC_HANDLING
   Diagnostics off: DEBUG, DEBUG_TRACE

   Nothing writes input to disk in this build. The view-tree diagnostics go
   over the control server on request and contain no input.


6. UPSTREAM FILES TOUCHED

   ui/views/window/dialog_delegate.h now befriends MouseMuxHelpDialog as well
   as MouseMuxControlDialog. DialogDelegateView's constructor is friends-only
   and WidgetDelegateView's has the same pattern, so a second dialog of ours
   has no other way to exist. That list carries a "DO NOT ADD TO THIS LIST"
   comment upstream; we are now two entries into it, and both need
   re-applying on a Chromium bump.

   ui/views/widget/desktop_aura/desktop_window_tree_host_win.cc gained a
   second exempt window handle, for the help window.


7. VERIFIED, AND NOT

   Verified on hardware:
     - two users, two mice, two keyboards, typing simultaneously
     - a claim filling its row immediately, which is what half of this
       release was about
     - screen numbers matching Windows' own numbering
     - the window title column showing the page each user is on

   NOT verified:
     - more than two users. The list is built for sixteen to twenty-four and
       nothing in the routing is limited to two, but that is inference.
     - pen and touch, still never run on hardware (unchanged since 2.2.53)
     - the mouse wheel on pages that scroll a nested element rather than the
       page itself. Wheel injection works - verified on an ordinary long page
       - and Gmail, where it was first noticed, does not respond. Nothing in
       this release touches the wheel path either way.
     - layouts other than US and ABNT2

   The known-good fallback remains 2.2.55 on Chromium 146.

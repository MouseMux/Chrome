MouseMux Chrome Patches v19 - Build #58 - 2026-09-02
=====================================================

Chromium base: 151.0.7922.77 (unchanged from 2.2.57)
Client version reported to the SDK: 2.2.58

A field report on 2.2.57 from a customer running two users found two things
wrong, both of them real. This release is those two fixes and the diagnostics
that should have been there to catch the first one.


1. KEYBOARDS REACHING THE WRONG WINDOW

   Reported as: with both users captured, both keyboards typed into the first
   user's window.

   Two independent causes, either of which produces exactly that.

   THE PAIRING MAY NOT EXIST. Every keystroke arrives carrying a KEYBOARD
   hwid, and all per-user state is keyed by MOUSE hwid, so the first thing
   OnKeyboardKey does is translate one to the other through
   keyboard_to_mouse_hwid_ - built from the SDK user list, from users that
   hold both a pointer and a keyboard. A user with a pointer alone produces no
   entry, and the lookup fails.

   The old fallback handed those keystrokes to owner_hwid_, the primary owner.
   That was correct while one device could drive Chrome: one owner, one
   possible destination, no guess involved. It silently became a guess when
   owners went plural, and the guess is always the same person - so with an
   unassigned keyboard, everybody types into the first user's window.

   With several owners we no longer guess. An unattributable keystroke is
   dropped, and so is one from a keyboard whose user owns no window - keyboard
   events were never gated on ownership, because with one owner the server's
   own hook meant only one keyboard could reach us. Both drops are recorded
   for the dialog. Losing a keystroke is recoverable; typing into a
   colleague's document is not.

   Single-owner behaviour is untouched: one window, one destination, nothing
   to get wrong.

   An unpaired keystroke also re-requests the user list, at most once every
   five seconds, so a pairing made in MouseMux while the browser is running is
   picked up rather than waiting for a restart. That finally uses
   last_user_list_request_, which had been declared and never referenced.

   THE CLAIM MAY NOT HAVE REACHED THE KEYBOARD. A click only set
   keyboard_target_view if it landed on page content. FindViewAtPoint finds
   web views; a click on a tab, the address bar, the toolbar or a bookmark
   goes down the aura path and returns before the line that follows a click
   with the keyboard.

   So a user whose first click landed on Chrome's own interface owned a window
   as far as the mouse was concerned and had no keyboard target at all - and
   fell through to "first showing view", which is a std::set iteration order,
   which is the earliest window, which is the first user again. Same symptom,
   entirely different mechanism, and the more likely of the two for anyone
   whose MouseMux configuration is correct.

   DispatchToAuraHost is now split: FindAuraTargetWindow() decides which
   toplevel window the click is in, DispatchToAuraHost() posts to it. The
   answer is needed before the click is sent, because two things depend on it.
   A mousedown there now claims that window for the device's keyboard, so
   clicking a tab picks a window up exactly as clicking the page does.

   And the hard lock applies on that path too. A click on another user's tab
   strip or toolbar is still a click in their window; this path was the way
   around the lock.

   The remaining unclaimed-keyboard fallback - a device that has genuinely not
   clicked anywhere - now drops with several owners rather than choosing
   somebody's window for them. Their row already says "not in a window yet".


2. DIAGNOSTICS, BECAUSE THE FIRST OF THOSE WAS INVISIBLE

   Neither cause can be seen from outside the browser, and the owner list made
   it worse by looking healthy: it showed where each user was WORKING, which
   is the same thing as where their typing lands only when the routing is
   right.

   Each owner row now shows the keyboard MouseMux has attached to that user -
   "no keyboard" when there is none, a tick once it has typed - and one line
   under the list shows where recent keystrokes actually went, window by
   window, or that they were ignored and why.

   Routing decisions only. No key codes, nothing that identifies a keystroke,
   which is why it stays on in release builds where per-key logging must not.
   Six entries, identical consecutive routes collapsed with a count, because a
   sentence of typing is one decision taken a hundred times.


3. "+ WINDOW" NOW HANDS OUT A SIGNED-IN WINDOW

   Reported as: sign in, press + Window, and the new window is signed out.
   Signing in there ends the first session, on a site that permits one.

   + Window called NewEmptyWindow. Cookies come from the profile so most sites
   carry over, but session storage belongs to the TAB, and a new window starts
   with an empty one. A web application holding its token there sees a new
   window as a new sign-in.

   It now duplicates the active tab and moves the copy to a new window, which
   is the customer's own workaround in one click. WebContents::Clone ->
   NavigationControllerImpl::CopyStateFrom clones the session storage
   namespace, and moving the tab carries the live WebContents across without a
   reload.

   Source is the first normal browser window, deliberately, not the most
   recently active one: under capture nothing is activating windows, so
   activation order is stale, while the first window is the one the operator
   signed in to. The copy is located by identity rather than by index, since
   pinning and tab groups move it. A tab that cannot be duplicated - a crashed
   one - still gets a blank window rather than nothing.

   CONSEQUENCE: sign in BEFORE handing windows out. A copy can only carry a
   session that already exists, and every handed-out window opens on whatever
   page the first window is showing. The README and the getting-started steps
   now say so.

   The copy reloads the page rather than photographing it, so state held only
   in the page's memory is not carried across. The session is.


4. DOCUMENTATION

   README rewritten in three places that were describing the product as it was
   two versions ago.

   "Windows and seats" replaces "Adding users, and adding seats" and leads
   with the question that actually decides it - should these people share a
   login - then explains what + Window copies and why signing in comes first.

   "Technical Details" claimed each user gets isolated cookies and history.
   That is what SEATS do and the opposite of what windows do, so it was
   actively misleading anyone choosing between them. Rewritten around device
   pairs, why capture is required, and a shared/not-shared table.

   "Privacy and session management" had the same inversion and now says
   plainly that windows of one browser are not private from each other by
   design.


5. NOT FIXED, AND KNOWN

   - Mouse wheel: a report that the wheel does not scroll. Not reproduced and
     not diagnosed; nothing in this release touches the wheel path.
   - Four users still untested. Two work.
   - Pen and touch still never run on hardware.

   The known-good fallback remains 2.2.55 on Chromium 146.

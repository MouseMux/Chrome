UPDATE v21 - keyboard through the window (branch keyboard-aura-routing)
=======================================================================

Started 2026-09-03. One entry per change, in order, each with the commit in the
Chromium tree (chrome-151-20260809/src) so any step can be reverted alone.
Build stamp #61 / 2.2.61 unless stated.

Every entry: WHAT changed, WHY (what was measured), and HOW TO REVERT.


1. Keyboard routed through the window            src commit 8cb777fd52e (snapshot)
----------------------------------------------------------------------------
What:   MOUSEMUX_AURA_KEYBOARD (mouse_mux_config.h, on). The controller no
        longer hands keys to the renderer; it posts WM_MOUSEMUX_KEYDOWN /
        KEYUP / CHAR to the user's window. DesktopWindowTreeHostWin::
        PreHandleMSG turns them into ui::KeyEvents flagged EF_IS_SYNTHESIZED
        and sends them where a real WM_KEYDOWN enters (the focus manager), and
        inserts characters straight into the focused TextInputClient.
        RenderWidgetHostViewEventHandler lets synthesized events past native
        keyboard blocking.
Why:    Keys reached only the page. The omnibox, find bar and browser shortcuts
        live in the views focus manager, which the renderer path never visits.
Revert: comment out #define MOUSEMUX_AURA_KEYBOARD; the old renderer path is
        the #else branch of InjectKeyboardEvent and still compiles.

2. OS-inactive window re-activated on the views side only     (same snapshot)
----------------------------------------------------------------------------
What:   Before dispatching a synthetic key to a window the OS has deactivated,
        PreHandleMSG runs HandleActivationChanged(true). During a synthetic
        key IsActive() reports true, Activate() and ClearNativeFocus() do
        nothing (g_mousemux_synthetic_key).
Why:    Measured with a foreground-window recorder: the OS foreground flipped
        between two users' windows on every keystroke. Stack traces showed the
        focus manager activating the widget (SetWindowPos) before it would
        focus a view in an inactive window, and View::OnFocus calling
        SetFocus(hwnd). With the overrides: zero activations in 669 keys.
Revert: remove the three g_mousemux_synthetic_key checks in
        desktop_window_tree_host_win.cc.

3. No OLE drag-and-drop from an injected mouse                 (same snapshot)
----------------------------------------------------------------------------
What:   g_mousemux_sdk_button_held (set by the controller while any injected
        mouse holds a button). WebContentsViewAura::StartDragging and
        DesktopDragDropClientWin::StartDragAndDrop refuse to start an OLE drag
        while it is set.
Why:    Field dump 2026-09-04 (other machine, "Chrome hangs"): UI thread in
        ole32!DoDragDrop under StartDragging. DoDragDrop ends only on a real
        button release; a captured device never produces one.
Cost:   an injected mouse cannot drag links, images or selected text out of
        a page or onto the bookmark bar. Selection itself is unaffected.
Revert: remove the two g_mousemux_sdk_button_held checks.

4. Chrome UI under an injected mouse                            (same snapshot)
----------------------------------------------------------------------------
What:   (a) SetForegroundWindow on synthetic clicks commented out in
        PreHandleMSG. (b) Mouse moves over non-page areas posted as
        WM_MOUSEMUX_MOUSEMOVE (about 60 Hz), WM_MOUSEMUX_MOUSELEAVE when the
        pointer leaves that window or returns to the page. (c) Before injecting
        into a page, an aura hit test (PageIsTopmostAt) checks that the page
        is what is on top; a child widget such as the find bar takes the
        window path instead.
Why:    (a) trace: menu_before=1, menu_after=0 on every menu click - activating
        the menu popup deactivated its owner and closed the menu. (b) menus and
        toolbar buttons never saw hover. (c) clicks on the find bar's X were
        injected into the page underneath.
Revert: (a) uncomment; (b) drop the kMouseMove case from the two dispatch
        conditions in InjectMouseEventToAnyView; (c) remove the PageIsTopmostAt
        call.

5. Virtual cursor                                               (same snapshot)
----------------------------------------------------------------------------
What:   g_mousemux_virtual_cursor_* (defined in ui/display/win/screen_win.cc,
        set by the controller on every injected mouse event, valid while
        anybody owns a window). ScreenWin::GetCursorScreenPoint() and aura's
        GetLastMouseLocationInRoot() (synthesized moves on window changes)
        answer with the injected pointer's position.
Why:    Chrome's menu asks "where is the mouse" when a submenu opens and
        re-selects from the answer; the real mouse idles elsewhere.
Note:   this alone did not stop the flicker; see 6.
Revert: remove the two reads; the definitions can stay.

6. Native moves and wheel blocked in Chrome UI while blocking   src dd46eb45a01
----------------------------------------------------------------------------
What:   The views-layer native block (MOUSEMUX_FULL_NATIVE_BLOCK) now drops
        WM_MOUSEMOVE, WM_MOUSEWHEEL and WM_MOUSEHWHEEL as well as the button
        messages. Dialog and help window remain exempt.
Why:    MOUSEMUX_MENU_TRACE stack traces: every deselect came from a NATIVE
        WM_MOUSEMOVE (HWNDMessageHandler::HandleMouseEventInternal) reaching
        the menu window, interleaved one-for-one with our moves. Windows
        re-posts an idle mouse's position to the window holding capture.
Cost:   while "Block native mouse input" is on, the operator's real mouse
        gets no hover in Chrome UI (it could not click there anyway).
Revert: revert commit dd46eb45a01.

7. Ownership routes the mouse                                   src 513d243572d
----------------------------------------------------------------------------
What:   A user who owns a window sends every mouse event to that window.
        Inside it, the point picks one of its own popups (its menu), its
        page, or its Chrome UI. Outside it, moves and releases still reach
        the page as under Windows capture; presses are dropped. The search
        over all windows by position (Z-order walk) survives only for a user
        who owns nothing yet.
Why:    Two overlapping windows: a click on the front window's toolbar was
        injected into the page of the window behind it (its rectangle
        contained the point; toolbars do not compete in a page search).
        Position-first routing predates ownership.
Cost:   switching windows is only possible via Release in the dialog; the
        "Keep each user in their own window" checkbox is now redundant and
        will be removed in a later step.
Revert: revert the commit alone.

8. Dialog always clickable; wheel follows ownership             src 60bce070bbb
----------------------------------------------------------------------------
What:   The MouseMux dialog and its help window are checked before the
        ownership rule: any user can click them whatever window they own.
        The wheel goes to the owned window's page wherever the pointer is,
        the same rule as clicks. Debug-only OWNED ROUTE log line per press.
Why:    Entry 7 dropped presses outside the owned window, and the dialog is
        outside it - nobody could release or toggle anything. The wheel was
        still picking a page by position, inconsistent with the rule.
Revert: revert the commit alone (loses both).

9. Users list: "Window N · title"                              src 5c507e1cc5d
----------------------------------------------------------------------------
What:   The row's window column leads with the window's number in the order
        the windows were opened, then the page title. The screen is gone.
Why:    two windows on the same page read identically (the title is the
        active tab's); the screen did not tell them apart.
Revert: revert the commit alone.

10. Screen pixels through Chrome's per-monitor mapping          src fe28a86e981
----------------------------------------------------------------------------
What:   Every MouseMux screen position is converted with
        display::win::ScreenWin::ScreenToDIPPoint (page injection, wheel,
        the unclaimed-user hit test, the owned-window page check) instead of
        pixels / this window's scale factor. PageIsTopmostAt no longer
        subtracts the window origin twice.
Why:    Customer screenshot 2026-09-03: pointer far left of a menu the page
        kept hovering. Chrome lays monitors out edge to edge in scaled units;
        on a monitor whose scaling differs from the primary's, the division
        lands a few hundred units off, so hover, clicks and the wheel act at
        the wrong spot. Right with one monitor or uniform scaling - which is
        why it appeared only with a third user on a third monitor.
Revert: revert the commit alone.

11. MOUSEMUX_ANONYMOUS_KEYS; stamp #62 / 2.2.62                 src d3fc4db9870
----------------------------------------------------------------------------
What:   With MOUSEMUX_DEBUG on, keys that produce text are logged as 'X'
        (vkey 0x58, scan 0, character U+0058) and raw MouseMux keyboard
        messages are not logged. Modifier, navigation and function keys
        are logged as they are. Comment the define out in
        mouse_mux_config.h for rich logging on the bench.
Why:    a debug build sent to a customer must not come back with a log
        that reads as what their users typed.
Package: chrome-release-2.2.62-debug-20260904 (field test for Gustavo).
Revert: comment out #define MOUSEMUX_ANONYMOUS_KEYS.

12. Logging that follows every event end to end                 src a46c70d7e14
----------------------------------------------------------------------------
What:   Under MOUSEMUX_DEBUG, four line kinds in mousemux_debug.log:
          IN     what arrived (device, user, raw screen pixels)
          ROUTE  the branch taken and why (owned window, popup, page,
                 Chrome UI, outside, drag lock, unowned search)
          OUT    what was handed to Chrome (view, host, scaled coordinates,
                 view bounds, widget coordinates, pending/ignoring state,
                 cross-process frame count)
          ACK    Chrome's answer to every input event of every registered
                 view (RenderWidgetHost::InputEventObserver): consumed,
                 not-consumed, NO-CONSUMER, IGNORED; ours=1 for injected
                 events (kFromDebugger), ours=0 for native
        Mouse moves every 50th per device (acks every 50th per host);
        everything else always. Keys carry user and window.
Why:    Gustavo's 2.2.62 logs showed every wheel event handed to the page
        and nothing about what the page did with it. The next field log
        must name the outcome.
Revert: revert the commit alone; no behaviour is involved.

13. A user owns a set of windows; one window, one owner         src 30b0a9c74ce
----------------------------------------------------------------------------
What:   Each user has a set of owned windows and one current window; all
        their input goes to the current one. A press inside another window
        of their own set makes it current (rectangle test against this
        user's windows only). A new window is adopted by its opener's owner
        (popups, links into new windows, print), else by the user whose
        injected input arrived last within 2 s (Ctrl+N, the menu); with no
        recent injected input it stays unowned. A window in somebody's set
        cannot be claimed by anyone else. A closed window leaves the set;
        the user is released only when the set is empty; Release hands back
        the whole set. Dialog row shows "+N" for extra windows.
Why:    a window the owner opened themselves (Ctrl+N, a site's login popup)
        could not be used: presses outside the single owned window were
        dropped. And two users could end up owning one window.
Revert: revert the commit alone.

14. The wheel's scroll gesture is ended                          src f4083facb85
----------------------------------------------------------------------------
What:   Per device, 100 ms after the last wheel notch, a zero-delta wheel
        event with phase Ended goes to the page the last notch went to
        (SendWheelEnd), as MouseWheelPhaseHandler does for a real mouse.
Why:    Every injected wheel was phase Began and nothing ever ended the
        gesture, so Chrome kept scrolling whatever the first notch latched
        onto - nothing, when that notch hit a spot without a scroller or
        the end of one. ACK log 2026-09-04: 206 consecutive "no consumer"
        on a page a real mouse scrolled at once; 447 scroll updates, 3
        scroll begins. This is the customer's "their wheel stops until I
        scroll there with my mouse".
Revert: revert the commit alone.

15. "[N] title" in every window caption                          src 33a055b3a3a
----------------------------------------------------------------------------
What:   A stable number per browser window (assigned when first seen, kept
        while it lives, keyed by session id) prefixed to the caption while
        MouseMux integration is on, and used by the dialog's "Window N".
        Header-only helper mouse_mux_window_number.h.
Why:    a person at a seat could not tell which window their row meant; and
        the dialog's numbering shifted when a window closed.
Revert: revert the commit alone.

16. "[Green] title": the owner's name in the caption              src 6d5464b02d8
----------------------------------------------------------------------------
What:   A window's caption starts with its owner's MouseMux name; with the
        window number while nobody owns it. Captions refresh on every
        ownership change, including a window joining a user's set.
Why:    the person at a seat had no way to see on the window that it was
        theirs (entry 15's number was not what was asked for).
Revert: revert the commit alone.
